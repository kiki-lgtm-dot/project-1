# 企业级数据获取系统方案 —— FetchBridge

> **文档用途**：甲方与开发团队对齐的沟通文件
> **项目命名**：FetchBridge（已开源：https://github.com/kiki-lgtm-dot/fetchbridge）
> **决策结论**：自主可控模式 —— 官方 API 打主力，自研工具做补充；代码完全自主可控；合规红线不可突破。
> **当前进度**：P1 试点（MVP）已完成 ✅；P2 生产化待推进 ⏳

---

## 1. 背景与目标

企业需要一个**自有、合规优先、可运维**的多平台数据获取系统，用于内部业务接入各平台的公开数据。

核心诉求：
- 官方 API 优先，不做绕风控/爬登录态的灰色方案
- 代码自主可控，出问题能自己修，不依赖外部个人维护者
- 全程审计、凭据零明文，满足企业安全与合规要求

---

## 2. 核心设计原则（FetchBridge 架构骨架）

| # | 原则 | 说明 | MVP 状态 |
|---|------|------|---------|
| 1 | **多后端路由** | 每个平台 =「首选 + 备选」有序列表，坏了自动切换，不重写代码 | ✅ |
| 2 | **体检机制（doctor）** | 一条命令体检所有平台，报告"当前在用哪个后端" | ✅ |
| 3 | **真实探活** | 实际发起请求验证可用性，而非只看依赖是否存在 | ✅ |
| 4 | **后端分级（tier）** | 官方 API=1 / 自研=2 / 开源兜底=3，明确优先级 | ✅ |
| 5 | **凭据零明文** | 密钥走 SecretProvider 抽象，配置文件强制剥离敏感字段 | ✅ 框架 |
| 6 | **渠道契约** | 一平台一模块，统一接口 | ✅ |

## 4. 系统架构（分层设计）

```
┌──────────────────────────────────────────────┐
│  调度层  任务队列 · 限频 · 重试 · 并发 · 审计  │
├──────────────────────────────────────────────┤
│  渠道层  web / github / rss / …               │  ← 一平台一模块，统一契约
├──────────────────────────────────────────────┤
│  路由层  「首选 + 备选」有序后端列表           │  ← 核心，自主维护
├──────────────────────────────────────────────┤
│  后端层  官方API(首选) → 自研 → 开源工具(兜底) │
├──────────────────────────────────────────────┤
│  数据层  统一清洗 · 脱敏 · 合规过滤 · 存储      │
└──────────────────────────────────────────────┘
```

**后端层优先级（每个平台都遵守）：**

```
官方 API  →  自研适配器  →  开源工具（仅作兜底）
  ✅首选        ✅次选          ⚠️末选（需法务单独评估）
```

---

## 5. 合规与安全红线（不可突破）

以下为**硬性要求**，任何技术方案不得绕过：

1. **只抓公开数据**：登录后可见内容、私密内容一律不碰
2. **官方 API 优先**：能用官方 API 的平台，不写绕风控方案
3. **法务书面背书**：每个目标平台的 ToS + 数据合规（PIPL/GDPR/CCPA）出书面结论后才开发
4. **个人信息脱敏**：入库前自动识别并脱敏姓名、联系方式等
5. **凭据零明文**：所有 Key/Cookie 走密钥系统，代码和日志中禁止出现
6. **专用账号池**：与员工个人账号、企业主账号完全隔离；配合频率控制与住宅代理
7. **全程审计**：抓取行为可追溯，日志保留周期合规

## 7. 验收标准

- [x] 每个平台后端遵循「官方 API → 自研 → 开源兜底」优先级（tier 分级已实现）
- [ ] 单平台后端失效后，路由层 **30 秒内自动切换** 到备选（MVP 已按序探测，未做定时失效缓存）
- [x] 体检命令可输出每个平台当前后端（`fetchbridge doctor`）
- [x] 凭据零明文（代码、日志、配置文件；生产需再接密钥系统）
- [x] 所有抓取行为有审计日志，可追溯
- [ ] 个人信息入库前完成脱敏（MVP 仅标记，未自动脱敏）
- [ ] 系统接入统一监控，失效 5 分钟内告警
- [ ] 依赖经内部制品库 + 安全扫描后引入，版本锁定

## 8. 待开发团队确认的问题

1. **目标平台清单**：P2 阶段首批接哪几个平台？（一律官方 API 优先）
2. **数据规模与频率**：日均抓取量级、并发要求？（决定调度层选型）
3. **技术栈**：密钥系统、监控、任务队列用什么？（Vault / Prometheus / Celery 等）
4. **部署环境**：本地、内网、还是云？（影响账号池与代理方案）
5. **法务进度**：目标平台的 ToS 结论以谁为准？
